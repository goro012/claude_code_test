# 08. アノテーション結果の活用

docs/07 で集めたアノテーション(Q1/Q2、必須/推奨・重要度の修正、不当の理由分類、足りない指摘、本番の指摘単位フィードバック)を、何にどう使うかを定めます。
活用先は6つあり、番号順に優先します。

## 0. 前提: 評価用と例示用を分ける

アノテーションをプロンプトの例示(4節)や受け入れ済み条件一覧(3節)に使うと、そのケースの再現率は「覚えた分」だけ高く出ます。

- 例示に使った期待指摘を持つ TestCase には `fewshot` タグを付ける。
- F1 はゲート指標(最終出力 必須再現率、誤抑制)を **`fewshot` を除いたケース** で計算し、全件の値は参考値として別に出す。
- 受け入れ済み条件一覧は雛形単位の知識であり特定ケースの暗記ではないため、除外しない。ただし一覧の元になった期待指摘だけで構成されたケース(雛形とほぼ同じ契約書)は `fewshot` 相当として扱う。

## 1. 回帰評価の分母にする

承認済の期待指摘が再現率の分母になります(docs/07 2節)。候補は「候補込み再現率」として参考表示し、ゲートには使いません。
ここは自動で、人の作業はありません。

## 2. プロンプトの「直す場所」を特定する

アノテーションの選択肢は、そのまま改善の分類になります。週次で理由分類ごとの件数を出し、**最多の分類から1つずつ** 直します。

| アノテーション | 意味 | 直す場所(プロンプト/フロー) |
|---|---|---|
| Q1 不当・理由「読み違え」 | 条項を誤読、存在しない条項を指摘 | 段階1に「指摘には対象条文を原文引用すること」を追加。子フローで引用が契約書テキストに含まれない指摘を落とす(決定的な後処理) |
| Q1 不当・理由「当社の立場では不要」 | 立場の扱いが弱い | 段階1の立場ルール(発注側/受注側で何を問題にし、何を問題にしないか)を表で明文化 |
| Q1 不当・理由「重複」 | 同一論点を分割している | 段階1に「同一条項・同一論点は1件に統合」を追加。子フローで条項 × カテゴリが同じ指摘を統合 |
| Q2 が Bot と食い違う: 人=非該当、Bot=該当(誤抑制) | 「該当」の定義が広すぎる | 段階2の該当の定義に境界事例を追加(緩和条項・上限付きは非該当、部分一致は非該当) |
| Q2 が Bot と食い違う: 人=該当、Bot=非該当(誤通過) | 「該当」の定義が狭すぎる | 同上、逆方向の例。受け入れ済み条件一覧(3節)に追加されれば自動で直ることが多い |
| 重要度の修正が多いカテゴリ | 重要度基準が伝わっていない | 段階1にカテゴリ × 立場ごとの重要度基準表を入れる(docs/05 3節と同じ文) |
| 必須/推奨の修正 | 評価側の基準 | プロンプトは変えない。期待指摘の必須/推奨を校正会で更新 |
| 「足りない指摘」が集中するカテゴリ | 観点が抜けている | 段階1のチェック観点に追加。批評パス(docs/07 5.1)の出力と突き合わせて、観点の文言を決める |
| 本番「表示すべきだった」 | 誤抑制の本番事例 | 誤抑制と同じ扱い。優先度1で F3 に流し、Q2 を確定させてから段階2を直す |

**1回のプロンプト変更で直す分類は1つ** にします。回帰の差分がどの変更によるものか読めるようにするためです。

## 3. 段階2の「受け入れ済み条件一覧」を作る(最も効く)

Q2 で「該当」と承認された期待指摘は、「この雛形版では、この論点のこの条件を当社は受け入れている」という事実です。
雛形ごとに集約して段階2のプロンプトに渡すと、LLM が毎回雛形全文から推論するより判定が安定します。

### 一覧の形

| 列 | 内容 |
|---|---|
| 雛形ID(版) | 対象の雛形 |
| カテゴリ | 例: 再委託 |
| 受け入れ済み条件(要約) | 例: 再委託には甲の書面による事前承諾が必要 |
| 雛形条項 | 例: 第10条 |
| 根拠 期待指摘 | 承認済 ExpectedFinding の ID(複数可) |
| 件数 | 何件の承認済指摘が裏付けているか |

Dataverse のビュー「受け入れ済み条件一覧(雛形別)」= ExpectedFinding で 状態=承認済 かつ 雛形該当=該当 を雛形 × カテゴリ × 雛形条項でまとめたもの。子フローが段階2の前にこのビューを取得し、プロンプトに「当社が受け入れている条件(この一覧に該当する指摘は applies_to_template = true)」として渡します。

同様に、状態=承認済 かつ 雛形該当=非該当 の行から「指摘すべき差分一覧(雛形別)」を作り、「雛形と異なるため指摘すべき条件」として渡します。こちらは雛形差分からの候補生成(docs/07 5.3)にも使います。

### 効果と注意

- プロンプト本文を書き換えずに、承認が増えるたびに段階2が育つ。
- 一覧は雛形の版に紐づく。雛形改版時は新版に対して再確認した行だけが一覧に入る(docs/06 5節)。
- 一覧が長くなったら(50 行超)、対象契約書の契約種別 × 立場で絞った上でカテゴリ順に並べる。段階1の指摘に含まれるカテゴリの行だけ渡すとさらに短くなる。
- 一覧との照合は LLM に任せるが、将来は「条項 × カテゴリが一覧と一致したら該当」の決定的な前処理に置き換えられる。

## 4. 例示(few-shot)として使う

承認済の期待指摘と対象条文の抜粋を、カテゴリ × 立場ごとに代表例として2〜3件ずつ段階1のプロンプトに入れます。

- **境界事例を優先する。** 校正会で割れて決着したもの、二重判定で最初は不一致だったものが最も価値がある。
- 例の形: 「条文抜粋 → 期待する指摘(タイトル、内容、提案、重要度)」。雛形該当の例は段階2のプロンプトに「条文抜粋 + 雛形条項 → 該当/非該当と理由」の形で入れる。
- 例の入れ替えはプロンプト版のマイナー更新として扱い、回帰で確認する。
- 件数が増えたら、契約種別 × カテゴリで Dataverse から絞って差し込む(Power Automate の「行を一覧」で十分。埋め込み検索は不要)。
- 例に使ったケースは `fewshot` タグで評価から外す(0節)。

## 5. 審査 LLM を校正する

Q1 の回答と審査の「一致/欠落」判定を突き合わせると、審査の誤りが分かります。

| 人 | 審査 | 意味 | 対応 |
|---|---|---|---|
| 一致していると判断(欠落に対し「Bot の○○が該当」とコメント) | 欠落 | 審査が対応を見逃した(条項ずれ、包含関係) | 審査プロンプトの照合ルールに例として追加 |
| 不当 | 一致 | 審査が緩い(論点が違うのに対応させた) | 「条項が同じでも論点が異なれば不一致」の例を追加 |

審査・人判定の一致率(docs/06 1節)が 90% を切ったときにだけ動けば十分です。審査プロンプトの変更は過去の EvalRun 1回分を再審査して、一致率が上がったことを確認してから切り替えます(docs/04)。

## 6. 業務側の資産に戻す

Bot の外でも価値があります。四半期に1回、開発者がまとめて法務に渡します。

| 還元先 | 元データ | 内容 |
|---|---|---|
| 雛形の弱点レポート | 承認済 かつ 雛形該当=該当 かつ 重要度=high | 「当社が受け入れている不利な条件」。雛形改版の材料 |
| レビューチェックリストの更新 | 「足りない指摘」、批評パスで妥当とされた指摘 | チェックリストに無かった観点 |
| 新任者の教材 | ルーブリックの境界事例、校正会の決定 | 「この条文はこう判断する」の実例集 |
| 利用者向け説明 | 本番「表示すべきだった」「非表示で正しい」の分布と理由 | 「なぜこの指摘が表示されないか」の説明文、非表示指摘の折りたたみの文言 |
| ゴールデンセット補強計画 | 本番フィードバックの契約種別 × カテゴリ分布 と カバレッジ表の空白 | 次に登録する契約書の種類 |

## 7. やらないこと

- **ファインチューニングを急がない。** 数百件規模では例示と受け入れ済み条件一覧の方が効き、ルーブリックが変わるたびに学習し直す負担が重い。承認済が 1,000 件を超え、ルーブリックが半年安定してから検討する。
- **1人の判定でプロンプトや承認済の期待指摘を直さない。** 候補 → 承認済の流れ(docs/07 6節)を守る。
- **一度に複数の分類を直さない。** 最多の分類を1つ直し、回帰で効果を確認してから次へ。
- **例示に使ったケースで再現率を語らない。** `fewshot` 除外後の値を正とする。

## 8. 週次集約フロー F6 の出力

F6(docs/03 8節)が承認済アノテーションから次の4点を生成し、校正会の前日に Teams へ投稿します。人はこれを見てプロンプトを直します。

1. **理由分類別の件数と最多分類** … Q1 不当の理由、Q2 不一致の方向、重要度修正、足りない指摘をカテゴリ別に集計。先週との差分付き。
2. **受け入れ済み条件一覧の差分** … 今週新たに一覧に入った行、雛形改版で外れた行。段階2の挙動が変わる箇所の予告になる。
3. **例示候補** … 今週校正会で決着した境界事例、二重判定で不一致から一致になった指摘。採用したら `fewshot` タグを付ける。
4. **審査不一致事例** … 5節の2パターンの一覧と、審査・人判定一致率。

## 9. 活用の流れ(まとめ)

```
アノテーション(Q1/Q2/修正/足りない指摘/本番FB)
   │
   ├─ 承認済 ExpectedFinding ──▶ 1. 回帰の分母(fewshot 除外)
   │        │
   │        ├─ 雛形該当=該当 ──▶ 3. 受け入れ済み条件一覧 ──▶ 段階2プロンプトへ自動供給
   │        ├─ 雛形該当=非該当 ─▶ 3'. 指摘すべき差分一覧 ──▶ 候補生成・段階2プロンプトへ
   │        └─ 境界事例 ────────▶ 4. 例示 ──▶ 段階1/段階2プロンプト(マイナー版)
   │
   ├─ 理由分類・修正の集計 ─────▶ 2. 直す場所の特定 ──▶ 最多分類から1つずつ修正
   ├─ Q1 と審査の突き合わせ ────▶ 5. 審査プロンプトの校正(一致率 90% 未満のとき)
   └─ high×該当・足りない指摘・本番FB ─▶ 6. 雛形弱点レポート、チェックリスト、教材、説明文(四半期)
```
