# 01. ループ設計

## 1. 現状と課題

| 項目 | 現状 |
|---|---|
| Bot | Copilot Studio、クラシックオーケストレーション |
| レビュー処理 | トピック → Power Automate フロー → カスタムコネクタ → Microsoft Foundry の LLM |
| プロンプトの所在 | カスタムコネクタ側 |
| 入力 | Word ファイルの契約書 |
| 処理の構造 | **段階1**: 対象契約書をレビューし指摘一覧を作る。**段階2**: 各指摘が法務部チェック済みの雛形契約書にも該当するかを判定し、該当する指摘は削除、該当しないものだけを出力する |
| 評価 | 業務部門が手動でチャットを試し、感想を返す |

ループが遅い原因は、**評価の毎周回に業務部門の人手が必要** なことです。
プロンプトを1行変えるたびに「業務部門に見てもらう」が発生し、待ち時間が支配的になります。

## 2. 2段階パイプラインと評価の対応

```
対象契約書 ──▶ 段階1: レビュー ──▶ 段階1指摘(全件) ──▶ 段階2: 雛形照合 ──▶ 最終出力
                                        │                      │              (雛形に非該当の指摘のみ)
                                        │                      └ 各指摘に applies_to_template を付与
                                        │
   評価で測るもの:                       ▼
   ・段階1 必須再現率 / 余分指摘数       段階1指摘 と 期待指摘(ExpectedFinding)を意味で照合
   ・段階2 一致率 / 誤抑制率 / 誤通過率   一致した指摘の applies_to_template と 期待の「雛形該当」を比較
   ・最終出力 必須再現率(主指標)         期待が「雛形非該当 かつ 必須」の指摘が最終出力に残っているか
```

| 段階 | 誤りの種類 | 利用者への影響 | 評価上の名前 |
|---|---|---|---|
| 段階1 | 指摘すべき論点を落とす | 見落とし | 段階1 欠落 |
| 段階1 | 不要・誤った指摘を出す | ノイズ、信頼低下 | 余分指摘(人判定 Q1 で妥当/不当を確定) |
| 段階2 | 雛形に該当しない指摘を「該当」として削除する | **利用者に見えなくなる。最も有害** | 誤抑制 |
| 段階2 | 雛形に該当する指摘を「非該当」として残す | ノイズ | 誤通過 |

段階2の誤抑制は最終出力から消えてしまうため、**最終出力だけを見る評価では検出できません**。
そのため子フローは抑制前の段階1指摘を全件返し、評価は段階1と段階2を別々に測ります。

## 3. 内側ループと外側ループ

```
┌──────────────── 内側ループ(開発者のみ・毎変更・数分) ────────────────┐
│  プロンプト修正 → F1 評価実行(直接モード) → 回帰結果を確認 → 修正   │
│         ▲                                                          │
│         └──── ゴールデンセット(TestCase + ExpectedFinding + Template) │
└────────────────────────────────────────────────────────────────────┘
                              │ 余分・欠落・誤抑制・誤通過 の指摘だけ
                              ▼
┌──────────────── 外側ループ(業務部門・週次・非同期) ─────────────────┐
│  F3 人判定依頼(Teams カード、指摘単位)                                │
│     Q1 この指摘は妥当か  Q2 雛形契約書にも該当するか                   │
│  → 校正会で割れた事例だけ議論 → ExpectedFinding とルーブリックを更新    │
│  F4 本番フィードバックのトリアージ → 採用分を TestCase 草案に自動作成   │
└────────────────────────────────────────────────────────────────────┘
```

- **内側ループ** は業務部門の関与ゼロで回ります。段階1の照合は LLM 審査(docs/04)、段階2の一致はフラグ比較で決定的に計算します。
- **外側ループ** は「審査と期待が割れた指摘」と「本番で不満が出たケース」だけを扱います。全件確認は行いません。
- **立ち上げ期**は例外で、新しいテストケースの Bot 出力を全指摘 Q1/Q2 で判定してもらい、その回答をそのまま ExpectedFinding にします(白紙から期待指摘を書かせない)。

## 4. 呼び出しの2モード

| モード | 経路 | 用途 | 速度 | 並列度 |
|---|---|---|---|---|
| 直接モード(既定) | F1 → 子フロー「レビュー実行」→ カスタムコネクタ → Foundry(段階1、段階2) | 毎変更の回帰 | 速い(1件 十数秒〜) | 5 程度 |
| E2E モード | F1 → Copilot Studio コネクタ「Execute Agent and wait」→ Bot 本体 → トピック → 子フロー | リリース前の本番経路確認 | 遅い(1件 数十秒〜) | 1〜2 |

直接モードを既定にする理由は、Bot のトピック分岐・添付ファイル処理・会話状態が評価結果に混ざらないようにするためです。
プロンプトの良し悪しだけを測れます。E2E モードは「本番と同じ経路で壊れていないか」を確認する用途に限定します。

### 子フロー化

既存のレビューフローから「LLM 呼び出し部分(段階1と段階2)」を子フローに切り出します。

- 入力: `contract_text`(契約書テキスト)、`prompt_version`(プロンプト版ラベル)、`contract_type`(契約種別)、`position`(当社の立場)、`template_id`(雛形ID。空なら契約種別と立場で Template テーブルを検索)
- 出力: `findings_json`(段階1指摘 全件 + 段階2判定、templates/findings_schema.json 準拠)、`display_text`(チャット表示用テキスト。`applies_to_template = false` のみ)、`model`、`template_id`、`template_version`

Bot のトピックと F1 の両方がこの子フローを呼びます。同じロジックを2か所に持たないことが重要です。

## 5. レビュー出力の構造化

審査を安定させるため、レビュー結果を **指摘一覧 JSON** として返し、チャット表示用テキストはそこから生成します。
段階2の判定は削除ではなくフラグとして持ちます。

```json
{
  "findings": [
    {
      "clause_ref": "第12条",
      "category": "損害賠償",
      "severity": "high",
      "title": "損害賠償額の上限が定められていない",
      "detail": "乙の損害賠償責任に上限がなく、当社の負担が無制限になり得る。",
      "suggestion": "「本契約に基づき受領した対価の総額を上限とする」旨を追記する。",
      "applies_to_template": false,
      "template_clause_ref": "第14条",
      "template_excerpt": "乙の損害賠償責任は、本契約に基づき乙が受領した委託料の総額を上限とする。",
      "template_reason": "雛形は上限を定めており、対象契約書とは異なるため非該当。"
    },
    {
      "clause_ref": "第9条",
      "category": "再委託",
      "severity": "medium",
      "title": "再委託に甲の書面承諾が必要",
      "detail": "…",
      "suggestion": "…",
      "applies_to_template": true,
      "template_clause_ref": "第10条",
      "template_excerpt": "乙は、甲の書面による事前の承諾なく、本業務を第三者に再委託してはならない。",
      "template_reason": "雛形も同じ条件を定めており、当社が受け入れている条件のため該当。"
    }
  ],
  "summary": "…"
}
```

- 2件目は段階2で「雛形に該当」と判定されたため最終出力には表示されませんが、JSON には残り、評価と人判定の対象になります。
- 利用者向けの表示(Markdown の表、アダプティブカード)は、どちらもこの JSON から子フローが生成します。LLM に表を直接書かせません(移行手順は docs/10 6節)。
- `template_excerpt` は人判定カード(F3)で業務判定者が Q2 を判断するために使います。段階2のプロンプトに「該当箇所を引用すること」を含めます。
- カテゴリと重要度の語彙は docs/05 のルーブリックで定義し、プロンプト側にも同じ語彙を渡します。
- 既存のカスタムコネクタが段階2の結果を「削除済みの一覧」でしか返していない場合は、段階2のプロンプトを「削除せず判定フラグと理由を付けて全件返す」に変更し、削除は子フロー側(表示用テキスト生成時)で行います。

## 6. 雛形契約書(Template)の扱い

- 雛形は Dataverse の Template テーブルで管理し、契約種別 × 当社の立場 × 版 で一意にします。
- TestCase は雛形を明示的に参照します。段階2の期待値(雛形該当/非該当)は雛形の版に依存するためです。
- 雛形の版が上がったら、その契約種別の ExpectedFinding の「雛形該当」を再確認する運用にします(docs/06)。
- Bot 経由(E2E)では契約種別と立場から有効な最新版を検索します。直接モードでは TestCase の参照を使い、版のずれをなくします。

## 7. Word 入力の扱い

- TestCase には **契約書テキスト(memo 列)** と **Word ファイルの参照(SharePoint ドキュメントライブラリの URL)** の両方を持ちます。
- 直接モードはテキストを使い、Word 解析の揺れを評価から切り離します。
- E2E モードは Word ファイルを Execute Agent の添付として送ります(添付転送は新しめの Copilot Studio バージョンが必要。docs/03 の前提チェック参照)。
- Word → テキスト変換は既存 Bot のフローで使っている手順をそのまま流用し、TestCase 登録時に一度だけ実行してテキスト列に保存します。変換処理の妥当性は「条項の抽出漏れがないか」の小さなチェック(条項番号の連番確認)で別途守ります。

## 8. Copilot Studio 組み込みの「エージェント評価」を使わない理由

Power Automate の Microsoft Copilot Studio コネクタには、組み込み評価を起動する
「Evaluate Agent」「Get Agent Test Run Details」アクションもあります。
ただしテストセットは `question` / `expectedResponse` の2列で、判定方法は完全一致・キーワード・意味類似のみです。

契約書レビューでは「期待する指摘が10件あり、そのうち必須の7件が含まれているか、雛形照合で正しく抑制されたか、余分な指摘が何件あるか」を測る必要があり、
1本の期待回答との類似度では評価できません。特に段階2の誤抑制は最終出力に現れないため、最終出力の類似度では検出不能です。
そのため本設計では自作の LLM 審査(docs/04)とフラグ比較を採用します。

組み込み評価は、挨拶・FAQ など単純応答のトピックがある別 Bot で併用する価値はあります。

## 9. 役割分担

| 役割 | 担当 | やること | やらないこと |
|---|---|---|---|
| 開発者 | 情報システム部門 | プロンプト修正、F1 実行、結果分析、校正会の進行 | 契約上の妥当性判断 |
| 業務判定者(2名以上) | 法務・契約担当 | Teams カードで指摘ごとに Q1/Q2 に回答(2営業日以内)、校正会参加(週30分)、TestCase 草案の仕上げ | プロンプト編集、全件確認 |
| 業務オーナー | 法務・契約担当の責任者 | ルーブリック(カテゴリ・重要度定義)の承認、雛形の版管理、リリース可否 | 日次作業 |
