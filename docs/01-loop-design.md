# 01. ループ設計

## 1. 現状と課題

| 項目 | 現状 |
|---|---|
| Bot | Copilot Studio、クラシックオーケストレーション |
| レビュー処理 | トピック → Power Automate フロー → カスタムコネクタ → Microsoft Foundry の LLM |
| プロンプトの所在 | カスタムコネクタ側 |
| 入力 | Word ファイルの契約書 |
| 評価 | 業務部門が手動でチャットを試し、感想を返す |

ループが遅い原因は、**評価の毎周回に業務部門の人手が必要** なことです。
プロンプトを1行変えるたびに「業務部門に見てもらう」が発生し、待ち時間が支配的になります。

## 2. 内側ループと外側ループ

```
┌──────────────── 内側ループ(開発者のみ・毎変更・数分) ────────────────┐
│  プロンプト修正 → F1 評価実行(直接モード) → 回帰結果を確認 → 修正   │
│         ▲                                                          │
│         └──── ゴールデンセット(TestCase + ExpectedFinding)を参照    │
└────────────────────────────────────────────────────────────────────┘
                              │ 審査スコアが低い / 余分指摘があるケースだけ
                              ▼
┌──────────────── 外側ループ(業務部門・週次・非同期) ─────────────────┐
│  F3 人判定依頼(Teams カード) → 同意/不同意 → 校正会で割れた事例だけ議論 │
│  F4 本番フィードバックのトリアージ → 採用分を TestCase 草案に自動作成   │
│  → 業務部門が ExpectedFinding を「Botの出力を直す」形で仕上げる       │
└────────────────────────────────────────────────────────────────────┘
```

- **内側ループ** は業務部門の関与ゼロで回ります。判定は LLM 審査(docs/04)が行います。
- **外側ループ** は「審査と人の判断が割れたケース」と「本番で不満が出たケース」だけを扱います。全件確認は行いません。

## 3. 呼び出しの2モード

| モード | 経路 | 用途 | 速度 | 並列度 |
|---|---|---|---|---|
| 直接モード(既定) | F1 → 子フロー「レビュー実行」→ カスタムコネクタ → Foundry | 毎変更の回帰 | 速い(1件数秒〜十数秒) | 5 程度 |
| E2E モード | F1 → Copilot Studio コネクタ「Execute Agent and wait」→ Bot 本体 → トピック → 子フロー | リリース前の本番経路確認 | 遅い(1件数十秒〜) | 1〜2 |

直接モードを既定にする理由は、Bot のトピック分岐・添付ファイル処理・会話状態が評価結果に混ざらないようにするためです。
プロンプトの良し悪しだけを測れます。E2E モードは「本番と同じ経路で壊れていないか」を確認する用途に限定します。

### 子フロー化

既存のレビューフローから「LLM 呼び出し部分」を子フローに切り出します。

- 入力: `contract_text`(契約書テキスト)、`prompt_version`(プロンプト版ラベル)、`contract_type`(契約種別、任意)
- 出力: `findings_json`(指摘一覧 JSON、templates/findings_schema.json 準拠)、`display_text`(チャット表示用テキスト)、`model`(使用モデル名)

Bot のトピックと F1 の両方がこの子フローを呼びます。同じロジックを2か所に持たないことが重要です。

## 4. レビュー出力の構造化

審査を安定させるため、レビュー結果を **指摘一覧 JSON** として返し、チャット表示用テキストはそこから生成します。

```json
{
  "findings": [
    {
      "clause_ref": "第12条",
      "category": "損害賠償",
      "severity": "high",
      "title": "損害賠償額の上限が定められていない",
      "detail": "乙の損害賠償責任に上限がなく、当社の負担が無制限になり得る。",
      "suggestion": "「本契約に基づき受領した対価の総額を上限とする」旨を追記する。"
    }
  ],
  "summary": "…"
}
```

- カテゴリと重要度の語彙は docs/05 のルーブリックで定義し、プロンプト側にも同じ語彙を渡します。
- 審査は「期待指摘 JSON」対「実際の指摘 JSON」で行うため、文言の揺れに強くなります。
- 既存のカスタムコネクタが自由文を返している場合は、プロンプトに JSON 出力指示を追加し、フロー側で `json()` でパースします。パース失敗は EvalResult に記録し、指標「JSON 整形失敗率」として追います。

## 5. Word 入力の扱い

- TestCase には **契約書テキスト(memo 列)** と **Word ファイルの参照(SharePoint ドキュメントライブラリの URL)** の両方を持ちます。
- 直接モードはテキストを使い、Word 解析の揺れを評価から切り離します。
- E2E モードは Word ファイルを Execute Agent の添付として送ります(添付転送は新しめの Copilot Studio バージョンが必要。docs/03 の前提チェック参照)。
- Word → テキスト変換は既存 Bot のフローで使っている手順をそのまま流用し、TestCase 登録時に一度だけ実行してテキスト列に保存します。変換処理の妥当性は「条項の抽出漏れがないか」の小さなチェック(条項番号の連番確認)で別途守ります。

## 6. Copilot Studio 組み込みの「エージェント評価」を使わない理由

Power Automate の Microsoft Copilot Studio コネクタには、組み込み評価を起動する
「Evaluate Agent」「Get Agent Test Run Details」アクションもあります。
ただしテストセットは `question` / `expectedResponse` の2列で、判定方法は完全一致・キーワード・意味類似のみです。

契約書レビューでは「期待する指摘が10件あり、そのうち必須の7件が含まれているか、余分な指摘が何件あるか」を測る必要があり、
1本の期待回答との類似度では評価できません。そのため本設計では自作の LLM 審査(docs/04)を採用します。

組み込み評価は、挨拶・FAQ など単純応答のトピックがある別 Bot で併用する価値はあります。

## 7. 役割分担

| 役割 | 担当 | やること | やらないこと |
|---|---|---|---|
| 開発者 | 情報システム部門 | プロンプト修正、F1 実行、結果分析、校正会の進行 | 契約上の妥当性判断 |
| 業務判定者(2名以上) | 法務・契約担当 | Teams カードへの回答(2営業日以内)、校正会参加(週30分)、TestCase 草案の仕上げ | プロンプト編集、全件確認 |
| 業務オーナー | 法務・契約担当の責任者 | ルーブリック(カテゴリ・重要度定義)の承認、リリース可否 | 日次作業 |
