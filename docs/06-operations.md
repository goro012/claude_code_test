# 06. 運用ルール、指標、リリース手順、立ち上げ計画

## 1. 指標

| 指標 | 定義 | 用途 |
|---|---|---|
| **最終出力 必須再現率(主指標)** | 期待が「雛形非該当 かつ 必須」の指摘のうち、Bot が段階1で一致し段階2で「非該当」と判定した割合。**ゲートには `fewshot` タグを除いたケースの値を使う**(docs/08 0節) | リリースゲート。利用者が実際に見る品質 |
| 候補込み 最終出力再現率 | 状態=候補の期待指摘も分母に含めた値 | 教師データが育つと主指標との差が縮む。参考値 |
| 段階1 必須再現率 | 段階1で一致した必須指摘 ÷ 必須総数 | 診断用。主指標が下がったとき段階1と段階2のどちらが原因かを切り分ける |
| 段階2 一致率 | 一致した指摘のうち、雛形該当の判定が期待と同じ割合 | 段階2の安定性 |
| **誤抑制率** | 期待が「非該当」の一致指摘のうち、Bot が「該当」として非表示にした割合 | 最も有害。利用者から見えなくなる |
| 誤通過率 | 期待が「該当」の一致指摘のうち、Bot が「非該当」として表示した割合 | ノイズ。利用者の「雛形と同じなのに」不満につながる |
| 余分指摘数(ケース平均) | 期待に無い段階1指摘 ÷ ケース数 | 過剰指摘の傾向 |
| 余分指摘の Q1 妥当率 | 人判定で「妥当」とされた余分指摘 ÷ 判定済み余分指摘 | 段階1の精度の代理。高ければ期待指摘の不足、低ければ Bot の過剰指摘 |
| Q2 と Bot 段階2の一致率 | 人判定 Q2 が Bot の `applies_to_template` と同じ割合(余分指摘を含む) | 段階2の信頼性。期待値の無い指摘でも測れる |
| 重要度一致率 | 重要度も一致した件数 ÷ 一致件数 | 重要度判定の安定性 |
| JSON 整形失敗率 | 段階1または段階2の失敗数 ÷ ケース数 | 0 が正常 |
| 平均応答時間 | 秒 | 体感品質。E2E モードで見る |
| 審査・人判定一致率 | 一致/欠落の判定について Q1 が審査と整合する割合 | 審査 LLM の信頼性。90% 未満で審査プロンプトを見直す |
| 判定リードタイム | F3 送信から回答までの日数 | 業務部門の負荷とボトルネックの把握 |

## 2. リリースゲート(F1 が自動判定)

不合格条件のいずれかに該当したら公開しない。

1. 最終出力 必須再現率が同モードの前回実行より `crv_FinalRecallThreshold`(初期値 0.05)以上低下した。
2. 重要ケース(`crv_iscritical = はい`)で、最終出力の必須指摘の欠落、または誤抑制が1件でもある。
3. JSON 整形失敗(段階1・段階2いずれか)が1件でもある。

ゲートは「前回より悪くなっていないか」を見るものです。絶対値の目標は立ち上げ後1か月の実測値をもとに業務オーナーと決めます。
誤抑制は主指標に含まれますが、重要ケース以外でも増加傾向なら Teams 通知に警告を出します(閾値: 前回比 +2 件)。

## 3. 段階1と段階2の切り分け

主指標が下がったときの読み方。

| 段階1 必須再現率 | 誤抑制率 | 原因 | 直す場所 |
|---|---|---|---|
| 低下 | 変化なし | 段階1が論点を落としている | 段階1プロンプト(レビュー観点) |
| 変化なし | 上昇 | 段階2が雛形に該当すると誤判定している | 段階2プロンプト(該当の定義、緩和条項の扱い) |
| 変化なし | 変化なし、誤通過率 上昇 | 段階2が抑制すべきものを通している | 段階2プロンプト |
| 変化なし | 変化なし、余分指摘 増加 | 段階1が過剰に指摘している | 段階1プロンプト。人判定 Q1 妥当率で「期待指摘の不足」でないか確認 |

## 3.5 改善サイクル(アノテーションからプロンプトへ)

1. F6 の週次投稿で「今週直す候補」(理由分類の最多)を確認する。
2. **1回の変更で直す分類は1つ**。docs/08 2節の対応表に従い、段階1または段階2のプロンプト(または子フローの決定的な後処理)を直す。
3. F1(直接)で回帰。`fewshot` 除外後の主指標と、直した分類の件数の減少を確認する。
4. 受け入れ済み条件一覧の差分は、プロンプトを変えなくても段階2の挙動を変える。F6 の投稿で差分が出た週は、プロンプト変更が無くても F1 を回してベースラインを更新する。
5. 例示(few-shot)の入れ替えはマイナー版として扱い、採用したケースに `fewshot` タグを付けてから F1 を回す。

## 4. プロンプト版ラベルの命名規則

`v<メジャー>.<マイナー>.<パッチ>` を段階1・段階2で共通に付けます(どちらを変えても上げる)。

| 変更内容 | 上げる桁 | 例 |
|---|---|---|
| カテゴリ・重要度の語彙変更、出力スキーマ変更、「雛形該当」の定義変更 | メジャー | v1.x → v2.0.0 |
| レビュー観点の追加・削除、段階2の判定基準の変更、モデル変更 | マイナー | v1.3.2 → v1.4.0 |
| 文言調整、例示の追加 | パッチ | v1.4.0 → v1.4.1 |

- ラベルはプロンプト本文の先頭行にコメントとして書き、子フローの `prompt_version` 入力にも同じ値を渡す。
- プロンプト本文はこのリポジトリの `prompts/` 配下(将来作成)に段階1・段階2・審査の3本を版ごとに保存し、EvalRun のメモに変更要約を書く。

## 5. 雛形の版管理

- 雛形は Template テーブルで版管理し、契約種別 × 立場ごとに「有効」は1件だけにする。
- 雛形が改版されたら: (1) 新版を Template に追加し旧版を退役、(2) その契約種別の TestCase の雛形参照を新版に付け替え、状態を「雛形要再確認」にする、(3) 変わった条項に関係する ExpectedFinding の「雛形該当」を業務判定者が見直す、(4) 見直し後に状態を「承認済」に戻し、F1 でベースラインを取り直す。
- EvalResult には実行時の雛形を記録しているため、版をまたいだ比較は行わない(前回比は同じ雛形版の実行同士で見る)。
- 改版後は受け入れ済み条件一覧(docs/08 3節)が新版で再確認した行だけになる。一覧が薄い間は段階2の一致率が下がり得るので、改版直後の F1 結果はベースラインとして扱わず、再確認が終わってから取り直す。
- 四半期に1回、ビュー「雛形弱点(high × 該当)」を法務に渡す(docs/08 6節)。雛形の改版材料になる。

## 6. リリース手順

```
1. プロンプト修正(段階1 / 段階2、ラベル更新)
2. F1 実行: mode=direct, tag_filter=空, review_scope=disagreements
   → ゲート合格まで 1〜2 を繰り返す(業務部門は不要)
3. F1 実行: mode=e2e, tag_filter=smoke(5〜10 件), review_scope=none
   → Bot 経路で壊れていないことを確認
4. Bot を公開
5. F1 実行: mode=e2e, tag_filter=空, review_scope=none
   → 合格したら EvalRun のメモに「公開済み」と記載
6. 手順2で送った F3 の人判定を待つ(2営業日)。議題が出たら校正会へ
```

公開前に業務部門の承認を待つ必要はありません。ゲート合格と E2E スモークが承認の代わりです。
ただし、メジャー版の変更(語彙・スキーマ・「雛形該当」の定義の変更)だけは業務オーナーの事前確認を取ります。

## 8. ゴールデンセットの育て方

- 目標規模: 立ち上げ時 20 件、3か月で 50 件。100 件を超えたら `regression-only` タグで日次実行から外す候補を作る。
- 構成の目安: 契約種別ごとに最低 3 件、発注側・受注側の両方、**雛形とほぼ同じ内容の契約書を 2〜3 件**(段階2が正しく全件抑制するかの確認用)、「指摘が無いはず」のクリーンな契約書を 2〜3 件(余分指摘の検出用)。
- 各ケースに「雛形該当 = 該当」の期待指摘を最低1件は含める(誤通過を測るため)。
- 退役: 同じ論点が 3 件以上重なったら古いものを退役(状態 = 退役)。削除はしない。
- 出所: 実契約書は匿名化(社名・個人名・金額・日付を置換)してから登録。合成契約書は雛形をベースに条項を改変して作ると、段階2の期待値が立てやすい。

## 9. 立ち上げ 2 週間計画

| 週 | 開発者 | 業務部門 |
|---|---|---|
| 1 週目 前半 | Dataverse テーブル作成、**Template に有効な雛形を登録**、子フロー切り出し(段階2を「削除」から「フラグ付与」に変更)、Bot トピック差し替え、F1(直接)作成 | 過去レビュー済み契約書 20 件の候補出し(匿名化前)、雛形の最新版の提供 |
| 1 週目 後半 | 20 件を Word → テキスト変換して TestCase 登録(草案、雛形参照を設定)。F1 を `review_scope=all` で実行し、F3 で全指摘の Q1/Q2 カードを送る | カードで Q1/Q2 に回答(1件 10〜20 分)。欠落している論点はコメントで追加 |
| 2 週目 前半 | F3 の後処理で作られた ExpectedFinding を確認し、コメントの追加論点を手で登録。TestCase を承認済に。F1 を回してベースライン EvalRun を作る | 「雛形該当 = 未確認」の行を埋める |
| 2 週目 後半 | F2・F4 作成、Bot にフィードバック質問を追加。審査プロンプトを人判定との一致率で調整 | 初回校正会(ルーブリックの語彙と「雛形該当」の境界事例を確定) |

2 週目終了時点の完了条件: ベースライン EvalRun が存在し、審査・人判定一致率が 90% 以上、全 TestCase の期待指摘に「雛形該当」が入っている、Bot にフィードバックボタンがある。

## 10. E2E モードで JSON が取れない場合

Bot の表示テキストは段階2で抑制された指摘を含まないため、表示テキストからは段階2を評価できません。E2E モードでは次のいずれかにします。

1. **E2E 評価用トピック**を用意する(推奨)。トリガー文「[EVAL]」で起動し、通常トピックと同じ子フローを呼んで `findings_json`(段階1全件 + 段階2判定)をそのまま返す。F1 の E2E モードはこのトピックに送る。本番利用者には案内しない。
2. E2E モードでは審査を行わず、「応答が返る」「応答時間」「表示された指摘数が直接モードの非該当件数と一致する」だけを確認する簡易チェックにする。

推奨は 1 です。Bot の経路(添付処理、トピック分岐、雛形検索、子フロー呼び出し)を通しつつ、直接モードと同じ審査ができます。

## 11. やらないこと

- 業務部門への「全件確認してください」の依頼(立ち上げ期の新規ケースを除く)。
- 会議で画面を共有しながら Bot を試す評価。
- 感想ベースの合否判定。判定はゲートと人判定の数字で行う。
- 最終出力だけを見た評価(段階2の誤抑制が見えない)。
- 契約書本文の Feedback テーブルへの保存。
