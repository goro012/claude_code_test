# 06. 運用ルール、指標、リリース手順、立ち上げ計画

## 1. 指標

| 指標 | 定義 | 用途 |
|---|---|---|
| 必須指摘 再現率(主指標) | 必須一致数 ÷ 必須総数 | リリースゲート。プロンプト改善の効果測定 |
| 推奨指摘 再現率 | 推奨一致数 ÷ 推奨総数 | 参考 |
| 余分指摘数(ケース平均) | extras 件数 ÷ ケース数 | 過剰指摘の傾向。増え続けたら精度低下のサイン |
| 重要度一致率 | 重要度も一致した件数 ÷ 一致件数 | 重要度判定の安定性 |
| JSON 整形失敗率 | 失敗数 ÷ ケース数 | 0 が正常。増えたらプロンプトの出力指示が壊れている |
| 平均応答時間 | 秒 | 体感品質。E2E モードで見る |
| 審査・人判定一致率 | 「審査に同意」÷(同意 + 不同意) | 審査 LLM の信頼性。90% 未満で審査プロンプトを見直す |
| 判定リードタイム | F3 送信から回答までの日数 | 業務部門の負荷とボトルネックの把握 |

## 2. リリースゲート(F1 が自動判定)

不合格条件のいずれかに該当したら公開しない。

1. 必須再現率が同モードの前回実行より `crv_MustRecallThreshold`(初期値 0.05)以上低下した。
2. 重要ケース(`crv_iscritical = はい`)で必須指摘の欠落が1件でもある。
3. JSON 整形失敗が1件でもある。

ゲートは「前回より悪くなっていないか」を見るものです。絶対値の目標(例: 必須再現率 0.9)は、立ち上げ後1か月の実測値をもとに業務オーナーと決めます。

## 3. プロンプト版ラベルの命名規則

`v<メジャー>.<マイナー>.<パッチ>`

| 変更内容 | 上げる桁 | 例 |
|---|---|---|
| カテゴリ・重要度の語彙変更、出力スキーマ変更 | メジャー | v1.x → v2.0.0 |
| レビュー観点の追加・削除、モデル変更 | マイナー | v1.3.2 → v1.4.0 |
| 文言調整、例示の追加 | パッチ | v1.4.0 → v1.4.1 |

- ラベルはプロンプト本文の先頭行にコメントとして書き、子フローの `prompt_version` 入力にも同じ値を渡す。
- プロンプト本文はこのリポジトリの `prompts/` 配下(将来作成)に版ごとに保存し、EvalRun のメモに変更要約を書く。

## 4. リリース手順

```
1. プロンプト修正(ラベル更新)
2. F1 実行: mode=direct, tag_filter=空(承認済み全件)
   → ゲート合格まで 1〜2 を繰り返す(業務部門は不要)
3. F1 実行: mode=e2e, tag_filter=smoke(5〜10 件)
   → Bot 経路で壊れていないことを確認
4. Bot を公開
5. F1 実行: mode=e2e, tag_filter=空
   → 合格したら EvalRun のメモに「公開済み」と記載
6. F3 の人判定結果を待つ(2営業日)。不同意が出たら校正会へ
```

公開前に業務部門の承認を待つ必要はありません。ゲート合格と E2E スモークが承認の代わりです。
業務部門の判定は公開後の外側ループで回収し、次のプロンプト版に反映します。
ただし、メジャー版の変更(語彙やスキーマの変更)だけは業務オーナーの事前確認を取ります。

## 6. ゴールデンセットの育て方

- 目標規模: 立ち上げ時 20 件、3か月で 50 件。100 件を超えたら `regression-only` タグで日次実行から外す候補を作る。
- 構成の目安: 契約種別ごとに最低 3 件、発注側・受注側の両方、「指摘が無いはず」のクリーンな契約書を 2〜3 件(余分指摘の検出用)。
- 退役: 同じ論点が 3 件以上重なったら古いものを退役(状態 = 退役)。削除はしない。
- 出所: 実契約書は匿名化(社名・個人名・金額・日付を置換)してから登録。合成契約書は実契約書の条項構造を真似て作る。本番フィードバック由来は利用者から匿名化済みテキストの再提供を受ける。

## 7. 立ち上げ 2 週間計画

| 週 | 開発者 | 業務部門 |
|---|---|---|
| 1 週目 前半 | Dataverse テーブル作成、子フロー切り出し、Bot トピック差し替え、F1(直接)作成 | 過去レビュー済み契約書 20 件の候補出し(匿名化前) |
| 1 週目 後半 | 20 件を Word → テキスト変換して TestCase 登録(草案)。Bot で 20 件を実行し出力を Excel に貼って渡す | Bot 出力を添削する形で ExpectedFinding を記入(1件 10〜20 分) |
| 2 週目 前半 | ExpectedFinding を取り込み、TestCase を承認済に。F1 を回してベースライン EvalRun を作る。F3 作成 | F3 の初回カード(無作為 10 件を含む)に回答 |
| 2 週目 後半 | F2・F4 作成、Bot にフィードバック質問を追加。docs/04 の審査プロンプトを人判定との一致率で調整 | 初回校正会(ルーブリックの語彙を確定) |

2 週目終了時点の完了条件: ベースライン EvalRun が存在し、審査・人判定一致率が 90% 以上、Bot にフィードバックボタンがある。

## 8. E2E モードで JSON が取れない場合

Bot の表示テキストからは指摘 JSON を復元できないことがあります。その場合は次のいずれかにします。

1. **E2E 評価用トピック**を用意する。トリガー文「[EVAL] レビュー」で起動し、通常トピックと同じ子フローを呼んで `findings_json` をそのまま返す。F1 の E2E モードはこのトピックに送る。本番利用者には案内しない。
2. E2E モードでは審査を行わず、「応答が返る」「応答時間」「必須カテゴリ名がテキストに含まれる」だけを確認する簡易チェックにする。

推奨は 1 です。Bot の経路(添付処理、トピック分岐、子フロー呼び出し)を通しつつ、直接モードと同じ審査ができます。

## 9. やらないこと

- 業務部門への「全件確認してください」の依頼。
- 会議で画面を共有しながら Bot を試す評価。
- 感想ベースの合否判定。判定はゲートと人判定の数字で行う。
- 契約書本文の Feedback テーブルへの保存。
