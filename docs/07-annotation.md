# 07. 教師データを育てるアノテーション設計

## 1. 問題の捉え方

業務部門からの教師データが弱い原因は、たいてい「業務部門の能力」ではなく **依頼の形** にあります。

| よくある依頼の形 | 起きること |
|---|---|
| 「この契約書の期待指摘を書いてください」(白紙) | 書く負荷が高く、粒度がばらつき、雛形該当まで書かれない |
| 「Bot の出力を見て感想をください」 | 「だいたい良い」で終わり、構造化されたデータにならない |
| 「全件確認してください」 | 後回しになり、締切間際に雑になる |

対策の原則は4つです。

1. **書かせない、直させる。** 常に Bot の出力(または LLM の下書き)を初期値にし、人は選択と修正だけをする。
2. **1回の接触で1行の教師データが増える。** 評価カード、本番チャット、校正会のどこで答えても、必ず ExpectedFinding の行が生まれるか更新される。
3. **自由記述は最後の1項目だけ。** 判定は選択肢で取り、理由は「選択肢 + 任意の1行」にする。
4. **聞く相手と件数を絞る。** 週の「アノテーション予算」(例: 判定者1人あたり 30 指摘)を決め、優先度の高いものから埋める。

## 2. 教師データの単位とライフサイクル

教師データは ExpectedFinding の行です。行に **状態** を持たせ、どの段階の行かを区別します。

```
候補(candidate) ──校正会 or 2人目の同意──▶ 承認済(approved) ──雛形改版/校正会──▶ 退役(retired)
   ▲                                          │
   │ Bot 出力への Q1=妥当                       │ 再現率の分母はここだけ
   │ 本番チャットの「違う」                      │
   │ LLM 下書きの承認                           │
   │ 過去レビュー資産からの抽出                  │
```

| 状態 | 生まれ方 | 評価での扱い |
|---|---|---|
| 候補 | Q1/Q2 の回答、本番フィードバック、LLM 下書き、過去資産の抽出 | 「候補込み再現率」を参考表示。ゲートには使わない |
| 承認済 | 2人目の判定者が同意、または校正会で確定 | 再現率とゲートの分母 |
| 退役 | 雛形改版で無効化、重複整理 | 集計外。削除しない |

ExpectedFinding に列を追加します(docs/02 への差分)。

| 表示名 | スキーマ名 | 型 | 説明 |
|---|---|---|---|
| 状態 | `crv_state` | 選択肢 | 候補 / 承認済 / 退役 |
| 自信 | `crv_confidence` | 選択肢 | 高 / 低(判定者の自己申告。低は校正会の議題) |
| 作成者 | `crv_createdby_annotator` | ユーザー参照 | 誰の判定から生まれたか |
| 確認者 | `crv_confirmedby` | ユーザー参照 | 2人目 |
| 生成元 Bot 版 | `crv_sourcepromptversion` | テキスト | どのプロンプト版の出力から作られたか |
| 生成元 評価指摘 | `crv_sourceevalfindingid` | 参照(EvalFinding) | 追跡用 |

## 3. アノテーションの入口を3つ用意する

### 3.1 評価カード(F3)を「添削」に寄せる

docs/03 の F3 カードを、判定だけでなく **修正済みの期待指摘がそのまま生まれる** 形にします。指摘1件あたりの UI:

```
[一致] 損害賠償 / high / 第12条                                  3 / 10
Bot の指摘: 損害賠償額の上限が定められていない
  乙の損害賠償責任に上限がなく…  提案: 対価総額を上限とする旨を追記
雛形 第14条: 「乙の損害賠償責任は…委託料の総額を上限とする」
Bot の判定: 雛形には該当しない → 表示する(雛形は上限を定めているため)

Q1 この指摘は妥当?   (●) 妥当  ( ) 不当  ( ) 判定不能
   不当の理由:        [▼ 読み違え / 当社の立場では不要 / 重複 / その他]
Q2 雛形にも該当?     ( ) 該当する  (●) 該当しない  ( ) 判定不能
必須/推奨:           (●) 必須  ( ) 推奨            重要度: [▼ high]
自信:                (●) 高  ( ) 低
▸ 内容を修正する(開くと title / description / suggestion が Bot の文で埋まった編集欄)
コメント(任意): [________________________________]
```

- 必須/推奨と重要度は Bot の値を初期値にして表示し、変えたいときだけ触る。
- 「内容を修正する」は `Action.ToggleVisibility` で折りたたむ。開かなければ Bot の文がそのまま期待指摘の文になる。
- 「不当の理由」は選択肢。これが段階1プロンプトの改善分類になる(読み違え → 条項抽出、立場で不要 → 立場の扱い、重複 → 統合指示)。
- 全指摘の後に1つだけ: **「足りない指摘はありますか?」** … 条項参照(テキスト)+ カテゴリ(選択)+ 内容(1行)+ 雛形該当(選択)。空でよい。

回答の反映(F3 後処理の差分):

| 種別 | 回答 | 生まれる/更新される行 |
|---|---|---|
| 余分 | Q1 = 妥当 | ExpectedFinding **候補** を新規作成(内容は編集後の文、雛形該当 = Q2、必須/推奨・重要度 = 回答値) |
| 余分 | Q1 = 不当 | EvalFinding に理由分類を記録。行は作らない。集計して段階1改善に使う |
| 一致 | 内容修正あり、または 必須/推奨・重要度・Q2 が期待と異なる | 期待指摘を直接は変えず、**修正提案** として EvalFinding に保持。校正会で承認したら反映(承認済の行を1人の判断で書き換えない) |
| 一致 | 修正なし | 期待指摘の「確認者」に判定者を記録(2人目の同意 → 候補なら承認済に昇格) |
| 欠落 | 必要 | 変更なし(Bot 側の問題) |
| 欠落 | 不要 | 期待指摘を退役候補として校正会議題 |
| 足りない指摘 | 入力あり | ExpectedFinding **候補** を新規作成(由来 = 判定者追加) |

### 3.2 本番チャットで「指摘単位」に聞く

会話の最後の「役に立ったか」では、どの指摘が悪かったのか分かりません。**指摘ごと** に聞き、さらに **非表示にした指摘** も見せて Q2 のラベルを集めます。

Bot の表示(Copilot Studio のアダプティブカード):

```
【high】第12条 損害賠償: 損害賠償額の上限が定められていない
   …
   [役に立った] [違う ▼ 読み違え / 当社には不要 / 雛形と同じ内容 / 重要度が違う]

【medium】…

▸ 雛形と同水準のため表示しなかった指摘が 2 件あります(開く)
   ・第9条 再委託: 再委託に甲の書面承諾が必要 … [表示すべきだった] [非表示で正しい]
```

- 「違う」の理由は選択肢。「雛形と同じ内容」は段階2の誤通過ラベル、「表示すべきだった」は誤抑制ラベルになります。誤抑制は最終出力に出ないため、**この折りたたみが本番で誤抑制を発見できる唯一の入口** です。
- 毎回全件を聞くと答えなくなるので、**1会話につき最大 2 指摘** をカードにボタン付きで出し、残りはボタン無し。選ぶ指摘は「段階2の判定理由が短い」「カテゴリの教師データが少ない」ものを優先(子フローが `ask_feedback: true` を付ける)。
- 回答は Feedback テーブルに **指摘単位** で記録します(docs/02 の Feedback に 指摘 JSON、指摘の評価、理由分類、非表示指摘への回答 を追加。docs/03 の F2 の入力も同じ)。
- 契約書本文は保存しません。F4 でテストケース化するときに匿名化済みテキストの再提供を依頼します。

### 3.3 まとめて片付ける画面(アノテーション キュー)

カードは「届いたものに答える」用です。まとまった時間に片付けたい人向けに、EvalFinding と Feedback を1つのキューに並べた画面を用意します。

- モデル駆動アプリのビュー「アノテーション待ち」(優先度順)+ フォーム上の Q1/Q2/必須/重要度/自信の選択肢。1件保存すると次の行が開くようにビジネスルールかキャンバスアプリで補助。
- 週次 Teams 要約に「あなたの待ち件数 n 件、今週の予算 30 件」と、この画面へのリンクを載せる。
- 最初は作らず、カードで回らなくなったら作る。

## 4. 何を優先して聞くか(アノテーション予算の配り方)

聞ける件数は限られるので、**教師データが最も増える・最も直る** ものから聞きます。F3 の対象抽出に優先度スコアを付けます。

| 優先度 | 条件 | 理由 |
|---|---|---|
| 1 | 誤抑制(Bot = 該当、期待 = 非該当)、および本番の「表示すべきだった」 | 利用者に見えない誤り。最も有害 |
| 2 | 余分指摘のうち、Bot 版を跨いで **出たり消えたりする** もの | プロンプト変更に敏感な境界事例。期待値を確定させる価値が高い |
| 3 | 期待指摘が少ない 契約種別 × カテゴリ の指摘 | カバレッジの穴を埋める |
| 4 | 段階2の期待が「未確認」の一致指摘 | 分母に入れられない行を減らす |
| 5 | 審査の `reason` が短い、または severity_match = false の一致指摘 | 審査の誤りを検出 |
| 6 | 候補状態の期待指摘に対応する一致指摘(2人目の同意で承認済に昇格) | 分母を増やす |
| 7 | 無作為 10% | 「怪しくない」ものが本当に正しいかの検算 |

優先度は EvalFinding に `crv_priority`(整数)として F1 が書き込み、F3 は予算(環境変数 `crv_WeeklyAnnotationBudget`)に達するまで高い順に送ります。

## 5. 人以外から候補を作る(LLM 下書き・過去資産)

教師データの弱さは「Bot が見つけていない論点」が期待指摘に無いことでもあります。Bot の出力だけを添削していると、その穴は埋まりません。人が承認するだけで済む **候補** を機械的に増やします。

### 5.1 チェックリスト駆動の批評パス

- 段階1とは別に、法務のレビューチェックリスト(カテゴリ × 立場ごとの確認項目)を1項目ずつ LLM に当てる「批評プロンプト」を用意し、TestCase に対して実行する(F1 とは別の任意フロー F5)。
- 出力は指摘 JSON と同じ形。段階1の指摘と審査で照合し、**段階1に無い指摘だけ** を EvalFinding(種別 = LLM 下書き)として F3 のカードに混ぜる。判定者は Q1/Q2 に答えるだけ。
- 妥当と答えられたものは候補になり、同時に「段階1が落としている論点」の証拠になる。

### 5.2 過去のレビュー資産からの抽出

- 過去にレビュー済みの契約書(修正履歴付き Word、コメント、レビューメモ)を LLM に渡し、「法務が付けた修正・コメントを指摘 JSON の形に変換」させる。
- 変換結果を、その契約書を TestCase として登録した上で EvalFinding(種別 = 過去資産)として F3 に流す。判定者は自分たちが過去に書いたものを承認するだけなので速い。
- 修正履歴・コメントの抽出は docx の XML から取れる(Power Automate では難しいため、初回はスクリプトで一括変換してよい)。

### 5.3 雛形との差分から候補を作る

- 対象契約書と雛形を LLM に渡し「雛形と異なる条項と、その差が当社に不利かどうか」を列挙させる。段階2の期待値(雛形該当 = 非該当)が付いた候補が直接生まれる。
- 合成テストケースを作るときも同じ発想で、雛形の条項を意図的に不利に改変した契約書を作れば、期待指摘と雛形該当が自動的に決まる。

## 6. 品質を保つ仕組み

| 仕組み | 内容 |
|---|---|
| 2人目の同意 | 候補 → 承認済 は別の判定者の同意か校正会の決定が必要。1人の判断で分母に入れない |
| 二重判定サンプル | 週の予算の 10% を2人に同じ指摘で送り、Q1/Q2 の一致率を測る。80% を下回ったらルーブリックの該当行を校正会で直す |
| 自信の自己申告 | 「自信: 低」は校正会に自動で上がる。判定者が迷いを隠さなくて済む |
| 選択肢優先 | 不当の理由、雛形該当、必須/推奨、重要度はすべて選択肢。自由記述は任意の1行のみ |
| 初期値は常に Bot | 編集欄は Bot の文で埋める。空欄を出さない |
| 判定ルール集 | 校正会で決めた境界事例を「ルール + 例」として docs/05 に追記し、同じ文を段階1・段階2のプロンプトにも入れる。ルーブリックとプロンプトを同じ文で揃える |
| 来歴の記録 | 誰が、いつ、どの Bot 版の出力から、どの雛形版で作った行かを残す。あとで「この版のときの判定」を追える |

## 7. 育っているかを見る指標(週次 Teams 要約に載せる)

| 指標 | 見方 |
|---|---|
| 承認済 期待指摘数(累計、週の増分) | 増えていなければ入口か予算が詰まっている |
| 候補の滞留数と平均滞留日数 | 校正会・2人目同意が追いついているか |
| カバレッジ表: 契約種別 × カテゴリ ごとの承認済件数 | 空白セルが優先度3の対象 |
| 雛形該当が「未確認」の割合 | 段階2の分母の健全性 |
| 二重判定の一致率(Q1、Q2 別) | ルーブリックの明確さ |
| 余分指摘の Q1 妥当率 | 高い = 期待指摘が足りない(教師データ側の問題)、低い = Bot の過剰指摘 |
| 判定者ごとの回答数と平均所要時間 | 負荷の偏り。所要時間が長い判定者はカードが読みにくい可能性 |
| 本番の指摘単位フィードバック数と「表示すべきだった」の件数 | 本番からの誤抑制検出が機能しているか |

## 8. 立ち上げ順(教師データが弱い状態から)

1. **既存資産の一括取り込み(1週目)** … 過去レビュー済み契約書 10〜20 件を 5.2 で候補化し、F3 で承認してもらう。白紙から書く工程をゼロにする。
2. **Bot 出力の全件 Q1/Q2(1〜2週目)** … 新規 TestCase は `review_scope=all` で回す。判定は選択のみ。
3. **本番の指摘単位フィードバック(2週目)** … 3.2 のカードを Bot に入れる。非表示指摘の折りたたみを必ず付ける。
4. **優先度付きの予算運用(3週目以降)** … 週 30 指摘、うち 10% 二重判定、10% 無作為。
5. **批評パス・雛形差分(4週目以降)** … カバレッジ表の空白セルを狙って候補を作る。

## 9. docs/02・docs/03 への差分まとめ

- ExpectedFinding: 状態(候補/承認済/退役)、自信、作成者、確認者、生成元 Bot 版、生成元 評価指摘 を追加。再現率の分母は「承認済」のみ。
- EvalFinding: 種別に「LLM 下書き」「過去資産」を追加。優先度、不当の理由分類、修正提案(title/description/suggestion/必須推奨/重要度/雛形該当の修正値)を追加。
- Feedback: 指摘単位の列(指摘 JSON、指摘の評価、理由分類、非表示指摘への回答)を追加。会話単位の「役に立った/違う」は残す。
- F1: EvalFinding に優先度を書き込む。候補込み再現率を参考値として EvalRun に追加。
- F2: 入力を指摘単位に拡張(finding_id、finding_rating、reason_code、hidden_finding_verdict)。
- F3: カードに 必須/推奨、重要度、自信、不当の理由、折りたたみ編集欄、足りない指摘 を追加。対象抽出を優先度順・予算制に変更。二重判定サンプルの送信。後処理を 3.1 の表に従って変更。
- 環境変数: `crv_WeeklyAnnotationBudget`(例 30)、`crv_DoubleAnnotationRate`(例 0.1)、`crv_ProductionAskPerConversation`(例 2)。
